---
title: LiteLLM
description: Send LiteLLM Gateway traces and metrics to Parseable using OpenTelemetry
---

LiteLLM Gateway provides an OpenAI-compatible proxy for many model providers. Its OpenTelemetry v2 callback exports GenAI spans, token usage, latency, cost, and errors to Parseable.

## Prerequisites

- Python 3.10 or later
- A Parseable instance and credentials
- A model-provider API key

## Create a trace dataset

```bash
curl -u "$PARSEABLE_USERNAME:$PARSEABLE_PASSWORD" \
  -X PUT "$PARSEABLE_URL/api/v1/logstream/litellm-traces" \
  -H 'X-P-Log-Source: otel-traces' \
  -H 'X-P-Telemetry-Type: traces' \
  -H 'X-P-Dataset-Tag: agent-observability'
```

Create a separate dataset for metrics:

```bash
curl -u "$PARSEABLE_USERNAME:$PARSEABLE_PASSWORD" \
  -X PUT "$PARSEABLE_URL/api/v1/logstream/litellm-metrics" \
  -H 'X-P-Log-Source: otel-metrics' \
  -H 'X-P-Telemetry-Type: metrics'
```

Traces and metrics require different `X-P-Log-Source` values and therefore cannot share one direct exporter configuration.

## Install LiteLLM and OpenTelemetry

```bash
pip install "litellm[proxy]" \
  opentelemetry-api \
  opentelemetry-sdk \
  opentelemetry-exporter-otlp-proto-http \
  opentelemetry-instrumentation-fastapi
```

Keep the OpenTelemetry API, SDK, exporter, and instrumentation packages on compatible release lines. Mixed versions can cause import or FastAPI instrumentation failures during proxy startup.

## Configure the gateway

Create `litellm-config.yaml`:

```yaml
model_list:
  - model_name: gpt-4o-mini
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: os.environ/OPENAI_API_KEY

litellm_settings:
  callbacks:
    - otel

# Metrics only: prevent request-specific attributes from creating a new time
# series for almost every call. Trace attributes are not affected.
callback_settings:
  otel:
    attributes:
      exclude_list:
        - hidden_params
        - metadata.requester_metadata
        - metadata.requester_ip_address
        - metadata.spend_logs_metadata
        - metadata.mcp_tool_call_metadata
        - metadata.vector_store_request_metadata
        - metadata.prompt_management_metadata
```

The `otel` callback is required. Setting `LITELLM_OTEL_V2=true` alone does not activate trace export.

Configure OTLP/HTTP and start the proxy:

```bash
export OPENAI_API_KEY="your-api-key"
export PARSEABLE_INGEST_URL="https://your-parseable-ingest-host:8000"
export PARSEABLE_BASIC_AUTH="$(printf '%s' 'admin:your-password' | base64)"

export LITELLM_OTEL_V2="true"
export OTEL_EXPORTER="otlp_http"
export OTEL_ENDPOINT="$PARSEABLE_INGEST_URL"
export OTEL_HEADERS="Authorization=Basic $PARSEABLE_BASIC_AUTH,X-P-Stream=litellm-traces,X-P-Log-Source=otel-traces"
export OTEL_SERVICE_NAME="litellm-proxy"
export OTEL_ENVIRONMENT_NAME="production"
export OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT="no_content"
export LITELLM_OTEL_INTEGRATION_ENABLE_METRICS="true"
```

The cardinality filter is important in production. Without it, attributes such as `hidden_params` and requester metadata can be close to unique per request, multiplying the number of metric series. Use an `include_list` instead when you need a strict allowlist. `include_list` and `exclude_list` are mutually exclusive, and `gen_ai.token.type` is always retained so input and output token series remain distinct.

The variables above configure the trace exporter. To send metrics directly to a separate Parseable dataset, install a global metrics provider before LiteLLM initializes its callback.

Create `sitecustomize.py` in the directory from which you start LiteLLM:

```python
import os

if os.getenv("LITELLM_OTEL_INTEGRATION_ENABLE_METRICS", "false").lower() == "true":
    from opentelemetry import metrics
    from opentelemetry.exporter.otlp.proto.http.metric_exporter import OTLPMetricExporter
    from opentelemetry.sdk.metrics import MeterProvider
    from opentelemetry.sdk.metrics.export import PeriodicExportingMetricReader
    from opentelemetry.sdk.resources import Resource

    reader = PeriodicExportingMetricReader(OTLPMetricExporter())
    provider = MeterProvider(
        metric_readers=[reader],
        resource=Resource.create(
            {"service.name": os.getenv("OTEL_SERVICE_NAME", "litellm")}
        ),
    )
    metrics.set_meter_provider(provider)
```

Then add the metrics exporter settings and put that directory on `PYTHONPATH`:

```bash
export OTEL_EXPORTER_OTLP_METRICS_ENDPOINT="$PARSEABLE_INGEST_URL/v1/metrics"
export OTEL_EXPORTER_OTLP_METRICS_HEADERS="Authorization=Basic $PARSEABLE_BASIC_AUTH,X-P-Stream=litellm-metrics,X-P-Log-Source=otel-metrics"
export OTEL_METRIC_EXPORT_INTERVAL="5000"
export PYTHONPATH="$PWD${PYTHONPATH:+:$PYTHONPATH}"

litellm --config litellm-config.yaml --port 4000
```

LiteLLM may start its proxy server in a child process. Loading the provider through `sitecustomize.py` ensures the child installs the metrics pipeline before the OpenTelemetry callback is created.

Send a request through the gateway:

```bash
curl http://localhost:4000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "Explain observability in one sentence."}]
  }'
```

For streaming metrics, make a real streaming request and consume the complete response:

```bash
curl -N http://localhost:4000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "stream": true,
    "messages": [{"role": "user", "content": "Explain tracing briefly."}]
  }'
```

Time-to-first-token and time-per-output-token metrics are conditional. They do not appear until LiteLLM processes a successful streaming response with the required timing and token data.

## Trace structure

OpenTelemetry v2 produces one distributed trace per proxy request. Depending on the route and enabled features, it can include:

```text
HTTP server request
├── authentication and routing
├── guardrails
├── cache or database work
└── LLM provider call
```

Health checks, the Prometheus scrape endpoint, UI assets, and documentation routes are excluded by default. Configure `OTEL_PYTHON_FASTAPI_EXCLUDED_URLS` if you need a different route policy.

LiteLLM accepts an inbound W3C `traceparent` header and continues the caller's trace. Set `OTEL_IGNORE_CONTEXT_PROPAGATION=true` only when every gateway request must start a new root trace.

## Fields exported

| Field | Meaning |
| --- | --- |
| `span_trace_id` | Trace identifier |
| `span_span_id` | Span identifier |
| `span_parent_span_id` | Parent span identifier |
| `span_duration_ns` | Request duration |
| `gen_ai.operation.name` | GenAI operation |
| `gen_ai.provider.name` | Model provider |
| `gen_ai.request.model` | Requested model |
| `gen_ai.response.model` | Model returned by provider |
| `gen_ai.usage.input_tokens` | Input tokens |
| `gen_ai.usage.output_tokens` | Output tokens |
| `litellm.cost.total` | Estimated request cost |

## Metrics exported

LiteLLM emits these GenAI histograms:

| Metric | Meaning |
| --- | --- |
| `gen_ai.client.operation.duration` | End-to-end LiteLLM operation duration |
| `gen_ai.client.response.duration` | Model response duration |
| `gen_ai.client.response.time_to_first_token` | Time to first streamed token |
| `gen_ai.client.response.time_per_output_token` | Average generation time per output token |
| `gen_ai.client.token.usage` | Input and output token usage |
| `gen_ai.client.token.cost` | Estimated request cost |

FastAPI instrumentation also emits HTTP server request, duration, size, and active-request metrics. Parseable keeps the original OpenTelemetry metric names, including dots, and exposes histogram `_bucket`, `_sum`, and `_count` series to PromQL.

The six `gen_ai.client.*` metrics are recorded for successful model calls. Failed authentication, unknown models, rate limits, and provider errors remain visible in HTTP and trace telemetry, but may not produce all GenAI usage or cost histograms because no successful model response exists.

### Histogram boundaries

OpenTelemetry SDK defaults may be too broad for sub-second durations or very small per-request costs. This can make a histogram quantile look much larger than the underlying observations. In production, configure OpenTelemetry `View` objects with explicit boundaries appropriate for seconds, tokens, USD, and bytes, or use an OpenTelemetry Collector/backend configuration that applies suitable histogram aggregation.

## Export LiteLLM proxy metrics

The OpenTelemetry callback emits the six `gen_ai.client.*` histograms above. LiteLLM also exposes broader gateway telemetry through its Prometheus callback, including proxy requests, authentication, deployments, fallbacks, routing, token usage, spend, budgets, rate limits, queues, Redis, and PostgreSQL metrics.

Install the Prometheus client and enable both callbacks:

```bash
pip install prometheus-client==0.20.0
```

```yaml
litellm_settings:
  callbacks:
    - otel
    - prometheus
```

LiteLLM exposes the metrics at `/metrics`. The endpoint requires the LiteLLM API key by default:

```bash
curl http://localhost:4000/metrics \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"
```

Use an OpenTelemetry Collector Prometheus receiver to scrape the endpoint and send the metrics to Parseable:

```yaml
receivers:
  prometheus/litellm:
    config:
      scrape_configs:
        - job_name: litellm
          scrape_interval: 15s
          static_configs:
            - targets: ["litellm:4000"]
          authorization:
            type: Bearer
            credentials: "${env:LITELLM_MASTER_KEY}"

processors:
  batch: {}

exporters:
  otlphttp/parseable_metrics:
    endpoint: "${env:PARSEABLE_INGEST_URL}"
    headers:
      Authorization: "Basic ${env:PARSEABLE_BASIC_AUTH}"
      X-P-Stream: litellm-metrics
      X-P-Log-Source: otel-metrics

service:
  pipelines:
    metrics/litellm:
      receivers: [prometheus/litellm]
      processors: [batch]
      exporters: [otlphttp/parseable_metrics]
```

This pipeline does not apply custom metric-name rewriting. LiteLLM metric names retain their underscore-based names and are not converted to Datadog-style dotted names. The Prometheus receiver does perform the standard Prometheus-to-OpenTelemetry data-model conversion:

- Prometheus labels become OpenTelemetry attributes.
- Counters may lose the conventional `_total` suffix in OTLP.
- Prometheus histograms become OpenTelemetry histogram data points.

The exact set of series is activity-dependent. For example, authentication failure metrics appear only after a failed authentication attempt. Generate representative success, error, streaming, fallback, and rate-limit traffic before validating coverage.

## Capture message content

`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` supports these LiteLLM modes:

- `no_content` — metadata only; recommended default
- `span_only` — content in span attributes
- `event_only` — content in span events
- `span_and_event` — content in both locations

<Callout type="warn">
  Message capture can store prompts and completions in Parseable. Enable it only after reviewing privacy, security, and retention requirements.
</Callout>

For a per-request override, pass `metadata.mask_input=true` or `metadata.mask_output=true`. The global `litellm_settings.turn_off_message_logging=true` setting is the strongest kill switch and suppresses captured request/response content even when the OpenTelemetry content mode enables it.

## Semantic conventions and compatibility

OpenTelemetry GenAI conventions are evolving. LiteLLM v2 emits canonical `gen_ai.*` fields and, by default, legacy-compatible fields as well. Relevant controls are:

```bash
# Opt into the latest experimental GenAI convention when your dashboards support it.
export OTEL_SEMCONV_STABILITY_OPT_IN="gen_ai_latest_experimental"

# Disable duplicate legacy-compatible attributes after migration.
export LITELLM_OTEL_LEGACY_COMPAT="false"
```

Test dashboard queries before changing either value. Attribute names, LLM span names, and event shapes can change when opting into a newer experimental convention.

## Semantic log events

LiteLLM can optionally emit OpenTelemetry semantic log events when `LITELLM_OTEL_INTEGRATION_ENABLE_EVENTS=true`. Events can contain prompt or completion content depending on the capture policy. Route them to a separate Parseable logs dataset using `X-P-Log-Source: otel-logs`; never send them to the trace or metrics dataset.

For production, use an OpenTelemetry Collector with independent traces, metrics, and logs pipelines. The direct `sitecustomize.py` example in this guide intentionally configures metrics only. Add a dedicated OpenTelemetry `LoggerProvider` or Collector logs pipeline before enabling events.

## Connect LiteLLM to an agent trace

Instrument the calling agent and propagate the W3C `traceparent` header to LiteLLM. Parseable can then display the agent, tool, gateway, and model spans as one trace. For a tested Pydantic AI setup, see [Pydantic AI](/docs/ingest-data/ai-agents/pydantic-ai).

## Verify metrics

Open the `litellm-metrics` dataset in the Metrics page. For API verification, list its metric names:

```bash
curl -u "$PARSEABLE_USERNAME:$PARSEABLE_PASSWORD" --get \
  "$PARSEABLE_URL/prometheus/api/v1/label/__name__/values" \
  --data-urlencode 'stream=litellm-metrics'
```

Histogram cards use `rate()` and `histogram_quantile()`. A short burst followed by an idle period can legitimately produce `NaN`, which the chart displays as **No data**. Generate sustained requests while validating rate-based charts.

`http.server.active_requests` is normally zero between requests because requests often complete before the periodic metrics export occurs.

The active-request instrument is a non-monotonic sum. Query its raw value rather than applying `rate()` when building a custom chart.

For production deployments, an OpenTelemetry Collector is an alternative to `sitecustomize.py`. Configure separate Collector exporters for traces and metrics so each signal receives the correct dataset and `X-P-Log-Source` header.

## Troubleshooting

### The dataset is not detected by Agent Observability

Confirm the dataset was created with all three headers:

- `X-P-Log-Source: otel-traces`
- `X-P-Telemetry-Type: traces`
- `X-P-Dataset-Tag: agent-observability`

### No spans arrive

Confirm `litellm_settings.callbacks` contains `otel`, `LITELLM_OTEL_V2` is `true`, and `OTEL_HEADERS` contains the Parseable stream and log-source headers.

### No metrics arrive

Confirm all of the following:

- `LITELLM_OTEL_INTEGRATION_ENABLE_METRICS` is `true`
- The metrics provider loads before LiteLLM's `otel` callback
- `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` ends in `/v1/metrics`
- Metrics headers use `X-P-Stream=litellm-metrics` and `X-P-Log-Source=otel-metrics`
- The trace and metrics datasets are different

### Proxy fails during OpenTelemetry initialization

Check installed OpenTelemetry package versions and align the API, SDK, exporter, and instrumentation packages on compatible release lines.

### Metrics have excessive cardinality

Inspect labels on `gen_ai.client.*` series. If request-specific values such as `hidden_params` or requester metadata are present, configure `callback_settings.otel.attributes.exclude_list` or a strict `include_list`, then restart LiteLLM.

### Streaming metrics are missing

Confirm the request uses `stream: true`, the client consumes the stream to completion, and the provider response contains timing and token usage information. Mock responses and non-streaming calls do not necessarily emit time-to-first-token or time-per-output-token.

### Debug exporter failures

Set `OTEL_DEBUG=true` temporarily. If spans print with `OTEL_EXPORTER=console`, LiteLLM instrumentation is working and the remaining issue is normally the endpoint, protocol, headers, TLS, or network path.
