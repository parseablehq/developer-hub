---
title: Manage Resources with Helm
description: Configure an Enterprise license, datasets, API keys, dashboards, alert targets, and alerts with Helm.
---

Use the Parseable Helm chart to manage datasets, API keys, dashboards, alert targets, and alerts from `values.yaml`.

## Prerequisites

- A Parseable installation: [OSS](/self-hosted/installation/distributed/k8s-helm-oss) or [Enterprise](/self-hosted/installation/distributed/k8s-helm-enterprise).
- `helm` and `kubectl` access to the cluster, and the `values.yaml` used for that installation.
- Administrator credentials in the Secret referenced by `parseable.store.secretName`. The provisioning Jobs use these credentials.

The examples use release and namespace `parseable`; replace these with yours.

**How the values work:**

- `enabled: true` applies the `items` list. Resources missing from that list are removed, including ones created in the UI.
- Omit a section or set `enabled: false` to leave that resource type unchanged. Check [later upgrades](#what-happens-on-later-upgrades) before removing items.

## Enterprise license (optional)

You can upload an Enterprise license in the Parseable UI. For Helm setup, use image `v3.2.7` or later and store the license JSON in a Secret:

```bash
kubectl create secret generic parseable-license \
  --namespace parseable \
  --from-file=parseable_license.json=./parseable_license.json
```

Add the Secret reference to your existing `parseable.enterprise` settings in `values.yaml`:

```yaml
parseable:
  enterprise:
    enabled: true
    image:
      tag: "v3.2.7" # Or a later Enterprise image version.
    license:
      secretName: parseable-license
      dataKey: parseable_license.json
```

- Helm uploads the license on each install or upgrade.
- If the Secret key is missing or the license is rejected, fix the error and rerun Helm.
- Without a license file, omit the `license` block.

## 1. Create a dataset

Add `datasets` under the existing `parseable:` key in `values.yaml`:

```yaml
parseable:
  # Keep your existing installation settings here, for example:
  # deploymentMode: distributed
  # store:
  #   type: s3-store
  #   secretName: parseable-env-secret

  # Add the dataset below under the same parseable: key.
  datasets:
    enabled: true
    items:
      - name: payment-logs
        telemetryType: logs
        logSource: json
        retention:
          duration: 30d
          action: delete
        # Enterprise only: enable when the querier has enough usable disk.
        # smartCache:
        #   size: 10Gi
```

| Field | Required? | Values and later changes |
| --- | --- | --- |
| `name` | Yes | Dataset name, such as `payment-logs`. Choose it carefully; renaming is not supported. |
| `telemetryType` | Yes | `logs`, `metrics`, or `traces`. Cannot change for an existing dataset. |
| `logSource` | Yes | `json`, `otel-logs`, `otel-metrics`, or `otel-traces`. An OTel source must match its telemetry type. Helm rejects a source absent from the existing dataset. |
| `retention.duration` / `.action` | No | `duration` is `1d` to `3650d`; `action` is `delete`. Omit `retention` to leave it unchanged. Use `duration: ""` or `duration: 0d` with `action: delete` to remove it. |
| `tags` | No | `agent-observability` requires `traces` with `otel-traces`. Enterprise reconciles tags on upgrade; OSS sets them on creation. |
| `smartCache.size` | No | Enterprise only; at least `10Gi` and enough usable querier disk. Omit `smartCache` to leave it unchanged; use `size: ""` or `size: 0Gi` to remove it. |

<Callout type="warn">
Keep dataset names unchanged. Replacing a name creates a new dataset and deletes the old dataset and its data.
</Callout>

## 2. Create API keys

Add `apiKeys` under the same `parseable:` key:

```yaml
parseable:
  # Existing installation settings stay here.
  apiKeys:
    enabled: true
    items:
      - name: payment-ingest
        apiKeyType: ingestor
      - name: payment-query
        apiKeyType: query
```

| `apiKeyType` | Access |
| --- | --- |
| `ingestor` | Ingestor of datasets. |
| `query` | Reader of all datasets. |

These are the two supported key types. Parseable assigns their global roles automatically; you do not configure roles for these keys in Helm.

<Callout type="warn">

Without `secretKeyRef`, Helm prints the generated key once. CI logs may retain it.
To supply a key, use a Secret as shown below.

</Callout>

### Provide your own key value

If you need to supply the value yourself, put a UUID v4 in a local `api-keys.env` file. You can add more API keys to the same file, one per line:

```dotenv
PAYMENT_INGEST_KEY=<generated-uuid-v4>
```

Create the Secret in the **same namespace** as Parseable:

```bash
kubectl create secret generic parseable-api-keys \
  --namespace parseable \
  --from-env-file=./api-keys.env
```

Then add a `secretKeyRef` to the API key entry:

```yaml
  apiKeys:
    enabled: true
    items:
      - name: payment-ingest
        apiKeyType: ingestor
        secretKeyRef:
          name: parseable-api-keys
          key: PAYMENT_INGEST_KEY
      - name: payment-query
        apiKeyType: query
```

`secretKeyRef.name` identifies the Kubernetes Secret; `secretKeyRef.key` identifies the field inside it. The value must be a hyphenated UUID v4.

## 3. Import a dashboard

Create a dashboard in the UI and export its JSON. Replace the sample names and JSON below with your own. For inline JSON:

```yaml
parseable:
  # Keep your existing installation settings here.
  dashboards:
    enabled: true
    items:
      - name: payments-dashboard
        json: |
          {"tiles": [], "tags": [], "sections": [], "variables": []}
```

`name` is the title shown in Parseable. Helm creates a ConfigMap for each inline dashboard.

If you prefer to keep the JSON in a separate ConfigMap, this example uses `traffic-analytics-dashboard.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: traffic-analytics-dashboard
  namespace: parseable
data:
  dashboard.json: |
    {"tiles": [], "tags": [], "sections": [], "variables": []}
```

Replace the example JSON with the full export, then run `kubectl apply -f ./traffic-analytics-dashboard.yaml`. Add it as another item:

```yaml
  dashboards:
    enabled: true
    items:
      - name: payments-dashboard
        json: |
          {"tiles": [], "tags": [], "sections": [], "variables": []}
      - name: Traffic Analytics
        configMap: traffic-analytics-dashboard
        namespace: parseable
```

Here, `name` sets the dashboard title in Parseable; `configMap` names the Kubernetes ConfigMap that holds its JSON.

For a ConfigMap source:

- Set `namespace`, even for the Helm release namespace.
- Put one JSON entry under `data`. The key can have any name.

<Callout type="warn">

Dashboards absent from `items` are deleted from Parseable, including UI-created ones.
`items: []` deletes all dashboards. External ConfigMaps stay in Kubernetes.

</Callout>

## 4. Create an alert target

Choose a target type: `webhook`, `slack`, or `alertManager`. This example uses a webhook. Put its endpoint in a local `alert-targets.env` file:

```dotenv
PAYMENTS_WEBHOOK_URL=https://example.com/your-webhook
```

Create the Secret in the **same namespace** as Parseable:

```bash
kubectl create secret generic parseable-alert-targets \
  --namespace parseable \
  --from-env-file=./alert-targets.env
```

Replace the example URL with your real endpoint. Add the target under `parseable:` in `values.yaml`:

```yaml
parseable:
  # Keep your existing installation settings here.
  targets:
    enabled: true
    items:
      - id: 01H7Z0XQ9G6K3JY1F5Z2X8V4E3
        title: payments-webhook
        type: webhook
        endpointSecretRef:
          name: parseable-alert-targets
          key: PAYMENTS_WEBHOOK_URL
```

| Field | Required? | Values and use |
| --- | --- | --- |
| `id` | Yes | Generate a 26-character ULID for this target and keep it unchanged. |
| `title` | Yes | Unique target name shown in Parseable. Cannot be changed in place. |
| `type` | Yes | `webhook`, `slack`, or `alertManager`. |
| `endpointSecretRef.name` / `.key` | Yes | Secret and key containing the endpoint URL. |
| `skipTlsCheck` | No | `true` or `false`; webhook and AlertManager only. |
| `customHeaders` | No | Header name/value pairs; webhook only. Do not put sensitive header values in Helm values. |
| `usernameSecretRef.name` / `.key` | No | AlertManager username Secret; use together with `passwordSecretRef`. |
| `passwordSecretRef.name` / `.key` | No | AlertManager password Secret; use together with `usernameSecretRef`. |

Slack targets use only `id`, `title`, `type`, and `endpointSecretRef`.

Run Helm to create the target before configuring the alert in the UI:

```bash
helm upgrade --install parseable parseable/parseable \
  --namespace parseable \
  --values ./values.yaml \
  --wait \
  --timeout 10m
```

This also applies the dataset, API key, and dashboard settings already in `values.yaml`. Save any newly generated API keys from the Helm output.

## 5. Create an alert

Create an alert in the UI, select the target, and export its JSON. The short JSON below is an example; replace it with the full export. For inline JSON:

```yaml
parseable:
  # Keep your existing installation settings here.
  alerts:
    enabled: true
    items:
      - json: |
          {"title": "payment-volume", "targets": ["01H7Z0XQ9G6K3JY1F5Z2X8V4E3"]}
```

The `targets` list uses the target ULID from step 4. Helm creates a ConfigMap for inline JSON.

To keep a different alert's JSON in a separate ConfigMap, save this example as `payment-alert.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: payment-errors
  namespace: parseable
data:
  alert.json: |
    {"title": "payment-errors", "targets": ["01H7Z0XQ9G6K3JY1F5Z2X8V4E3"]}
```

Replace the sample JSON with that alert's complete export, then run `kubectl apply -f ./payment-alert.yaml`. Add it as another item:

```yaml
  alerts:
    enabled: true
    items:
      - json: |
          {"title": "payment-volume", "targets": ["01H7Z0XQ9G6K3JY1F5Z2X8V4E3"]}
      - configMap: payment-errors
        namespace: parseable
```

For a ConfigMap source:

- Set `namespace`, even for the Helm release namespace.
- Put one JSON entry under `data`. Its key can have any name; no label is needed.
- `targets` must contain target ULIDs.

## 6. Apply the configuration

The full `parseable:` block now looks like this. Keep your deployment and storage settings. Replace the short JSON examples with complete exports before applying:

```yaml
parseable:
  # Your existing installation settings remain here.
  datasets:
    enabled: true
    items:
      - name: payment-logs
        telemetryType: logs
        logSource: json
        retention:
          duration: 30d
          action: delete
        # Enterprise only:
        # smartCache:
        #   size: 10Gi

  apiKeys:
    enabled: true
    items:
      - name: payment-ingest
        apiKeyType: ingestor
      - name: payment-query
        apiKeyType: query

  dashboards:
    enabled: true
    items:
      - name: payments-dashboard
        json: |
          {"tiles": [], "tags": [], "sections": [], "variables": []}
      - name: Traffic Analytics
        configMap: traffic-analytics-dashboard
        namespace: parseable

  targets:
    enabled: true
    items:
      - id: 01H7Z0XQ9G6K3JY1F5Z2X8V4E3
        title: payments-webhook
        type: webhook
        endpointSecretRef:
          name: parseable-alert-targets
          key: PAYMENTS_WEBHOOK_URL

  alerts:
    enabled: true
    items:
      - json: |
          {"title": "payment-volume", "targets": ["01H7Z0XQ9G6K3JY1F5Z2X8V4E3"]}
      - configMap: payment-errors
        namespace: parseable
```

After applying the dashboard and alert ConfigMaps, run the same Helm upgrade again:

```bash
helm upgrade --install parseable parseable/parseable \
  --namespace parseable \
  --values ./values.yaml \
  --wait \
  --timeout 10m
```

This upgrade imports the alert and reconciles the resources already configured.

## What happens on later upgrades?

An omitted or disabled section leaves its resources unchanged. With `enabled: true`, `items` is the complete desired list. Review removals before upgrading:

| Resource | Omitted or disabled | `items: []` or removed entry |
| --- | --- | --- |
| `datasets` | Datasets are left alone. | Deletes all deletable user datasets, or the removed dataset and its data. |
| `apiKeys` | Keys are left alone. | Revokes all API keys, or the removed key. |
| `targets` | Targets are left alone. | Requests deletion of all targets, or the removed target after alerts are reconciled. The server rejects deletion while an alert still uses it. |
| `dashboards` | Dashboards are left alone. | Deletes all dashboards, or the removed dashboard, including UI-created ones. External Kubernetes ConfigMaps remain. |
| `alerts` | Alerts are left alone. | Deletes all alerts, or the removed alert, including UI-created ones. External Kubernetes ConfigMaps remain. |

Keep target IDs unchanged when editing targets. If an upgrade fails, fix the error and run the same Helm command again.

Changing an external ConfigMap alone does not rerun the provisioning Job. Run `helm upgrade` to apply the updated JSON in Parseable.
